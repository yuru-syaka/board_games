 0. 全体像
--------------------------------------------------------------------------------

今回デプロイしたスタック（CDK の管理単位）は次の 3 つです。

  スタック名        リージョン            役割
  ---------------  --------------------  ------------------------------------------
  WebStack         東京 ap-northeast-1   サイト配信（S3 + CloudFront）
                                         → 今回「セキュリティ用ヘッダー」を追加
  SecurityStack    東京 ap-northeast-1   新規。CloudTrail / GuardDuty /
                                         IAM Access Analyzer / 通知用 SNS
  MonitoringStack  米国東部 us-east-1    新規。CloudFront の監視アラーム / 通知用 SNS

MonitoringStack だけ us-east-1 にある理由:
  CloudFront は世界共通のサービスで、その数値（メトリクス）は us-east-1 にしか
  記録されません。そのため、CloudFront を監視するアラームも us-east-1 に作る必要があります。
  あわせて us-east-1 でも「cdk bootstrap」（CDK が使う準備用の置き場の作成）を行いました。

追加・変更したファイル:
  infra/bin/infra.ts            3 つのスタックの組み立て、通知先の読み込み
  infra/lib/web-stack.ts        セキュリティヘッダーを追加

  infra/lib/monitoring-stack.ts 新規
  infra/config.local.json       新規（通知先メール。git 管理外）

 1. CloudFront のセキュリティ用レスポンスヘッダー（WebStack）
--------------------------------------------------------------------------------

【何をしたか】
  CloudFront の「レスポンスヘッダーポリシー」を作り、サイトのすべてのページと
  ファイルに、次のヘッダーを付けるようにしました。

  ヘッダー                               値 / 効果
  -------------------------------------  ---------------------------------------------
  Strict-Transport-Security              max-age=31536000（1 年）
                                         → ブラウザに「このサイトには常に HTTPS で
                                           接続する」と覚えさせる
  X-Content-Type-Options                 nosniff
                                         → ファイルの種類をブラウザが勝手に推測しない
                                           （画像に見せかけたスクリプトの実行などを防ぐ）
  X-Frame-Options                        SAMEORIGIN
                                         → 他のサイトの iframe に埋め込まれるのを防ぐ
                                           （クリックジャッキング対策）
  Referrer-Policy                        strict-origin-when-cross-origin
                                         → 外部サイトへ移動するとき、URL のパス部分を渡さない
  Permissions-Policy                     camera=(), microphone=(), geolocation=(), payment=()
                                         → カメラ・マイク・位置情報・決済の機能を使わせない
  Content-Security-Policy-Report-Only    読み込んでよいファイルの出どころを指定（下記）
                                         → 現在は「報告のみ」。違反があっても止めず、
                                           ブラウザのコンソールに表示するだけ

【CSP（Content-Security-Policy）の内容】
  default-src 'self'                       基本は自サイトのファイルだけ
  script-src 'self' 'unsafe-inline'        Unity の起動スクリプト（ページ内に直接書かれたもの）と
            'wasm-unsafe-eval' blob:       WebAssembly の実行を許可
  style-src 'self' 'unsafe-inline'
            https://fonts.googleapis.com   Google Fonts の CSS
  font-src  'self' https://fonts.gstatic.com
  img-src   'self' data: blob:
  media-src 'self' blob:
  connect-src 'self' blob: data:           PUN2（Photon Cloud）への通信を許可
            https://*.exitgames.com wss://*.exitgames.com
            https://*.photonengine.io wss://*.photonengine.io
  worker-src 'self' blob:
  frame-ancestors 'self'
  object-src 'none'
  base-uri 'self'

  「報告のみ」にした理由:
    Unity WebGL は特殊な読み込み方をするため、いきなり強制すると、ゲームが
    起動しなくなるおそれがあるためです。しばらく様子を見て、違反が出ないことを
    確かめてから、強制（Content-Security-Policy）に切り替えます。

【確認結果】
  - curl で、6 つのヘッダーがすべて付いていることを確認しました。
  - ブラウザでプレイページを開き、ゲームの起動と「オンライン対戦」（Photon への接続）を
    行いました。コンソールに CSP 違反のメッセージは出ていません。

【料金】 無料

 2. CloudTrail：操作の記録（SecurityStack）
--------------------------------------------------------------------------------

【何をしたか】
  証跡名「management-trail」を作り、AWS アカウントで行われた操作の記録
  （管理イベント）を、専用の S3 バケットに保存するようにしました。

  設定項目                     値                  理由
  ---------------------------  ------------------  ------------------------------------
  対象リージョン               全リージョン        東京以外で不審な操作があっても記録する
  グローバルサービスのイベント 含める              IAM・CloudFront などの操作も記録する
  管理イベント                 読み取り + 書き込み すべての設定変更とログインを記録する
  データイベント               記録しない          有料のため（S3 のファイル単位の操作など）
  ログファイルの検証           オン                記録が改ざんされていないか検証できる
  CloudWatch Logs への転送     オフ                有料のため。必要になったら有効にする
  保存先バケット               専用の S3 バケット  非公開、暗号化、HTTPS のみ
  保存期間                     365 日で自動削除    保存料を抑えるため
  スタック削除時               バケットは残す      監査記録を誤って消さないため

【なぜ必要か】
  アカウントの乗っ取りや誤操作があったときに、「いつ・誰が・どこから・何をしたか」を
  後から確認するためです。標準でも直近 90 日分は見られますが、それより古い記録は
  証跡を作っておかないと残りません。

【確認結果】
  ログ記録中（IsLogging = True）、マルチリージョン・ログ検証・グローバルイベントが
  すべて有効であることを確認しました。

【料金】
  1 つ目の管理イベントの証跡は無料です。S3 の保存料だけで、月に数円程度の見込みです。

【確認方法】
  コンソール: CloudTrail → 証跡 → management-trail
  操作の履歴: CloudTrail → イベント履歴

 3. GuardDuty：不審な動きの自動検知（SecurityStack）
--------------------------------------------------------------------------------

【何をしたか】
  東京リージョンで GuardDuty を有効にしました。

  検知する対象              状態      備考
  ------------------------  --------  ---------------------------------------------
  CloudTrail（操作の記録）  有効      基本機能（不審なログイン、権限の悪用など）
  VPC フローログ            有効      基本機能（不審な通信）
  DNS ログ                  有効      基本機能（マルウェアの通信先への問い合わせなど）
  S3 保護                   有効      S3 への不審なアクセス
  EKS / RDS / Lambda /      無効      使っていないサービス。費用を抑えるため
  マルウェア / ランタイム
  / AI 関連

  検出結果の更新頻度: 1 時間ごと

【通知】
  EventBridge のルールを作り、重要度 4（中）以上の検出結果があったら、
  SNS からメールで通知するようにしました。メールには、重要度・タイトル・種類・
  リージョン・説明が載ります。
  （GuardDuty の重要度: 1〜3.9 = 低、4〜6.9 = 中、7〜8.9 = 高、9 以上 = 重大）

【なぜ必要か】
  漏れた認証情報の悪用、仮想通貨のマイニング、普段と違う国からのアクセスなどを、
  人が監視しなくても自動で見つけて知らせてくれるためです。

【料金】
  最初の 30 日間は無料です。その後は記録の量に応じた課金で、この規模なら
  月に数十円〜数百円程度の見込みです。
  無料期間中に「GuardDuty → 使用状況」で、月額の見込みを確認してください。

【確認方法】
  コンソール: GuardDuty → 検出結果（通常は 0 件）
  通知のテスト: GuardDuty → 設定 → 「検出結果サンプルの生成」
    → サンプルの検出結果がメールで届けば、通知の経路は正常です
    （サンプルは大量に届くので、試すのは 1 回だけにしてください）

 4. IAM Access Analyzer：外部公開の検出（SecurityStack）
--------------------------------------------------------------------------------

【何をしたか】
  アナライザー「account-external-access」（種類: 外部アクセス、信頼ゾーン: このアカウント）を
  作りました。

【なぜ必要か】
  S3 バケット、IAM ロール、SNS トピックなどが、意図せずアカウントの外から
  使える状態になっていないかを、自動で調べ続けてくれます。

【料金】 無料（外部アクセスの分析）

【確認方法】
  コンソール: IAM → Access Analyzer → 検出結果
  CloudFront 用の S3 バケットは「CloudFront からだけ読める」設定なので、
  検出されても「CloudFront サービスからのアクセス」として表示されます。
  意図しない検出があれば、内容を確認して設定を見直してください。

 5. CloudFront の監視アラーム（MonitoringStack / us-east-1）
--------------------------------------------------------------------------------

【何をしたか】
  CloudWatch のアラームを 3 つ作り、しきい値を超えたとき（ALARM）と、
  元に戻ったとき（OK）にメールで通知するようにしました。

  アラーム                 条件                                    想定している事態
  -----------------------  --------------------------------------  -----------------------
  CloudFront5xxRate        5xx エラー率が 5 分平均で 5% 超を        サイトが壊れている
                           3 回連続（15 分間）                     （ファイルがない、設定ミス）
  CloudFrontDailyTraffic   配信量が 1 日で 50GB 超                 想定外の大量アクセス
                           （無料枠 1TB/月 ≒ 33GB/日 を超えるペース）（料金が増えるおそれ）
  CloudFrontRequestSpike   リクエストが 5 分間で 50,000 件超        短時間のアクセス集中
                                                                   （いたずら・攻撃の兆候）

  データがないとき（アクセスがないとき）は「正常」とみなします。
  作成直後は「データ不足（INSUFFICIENT_DATA）」と表示されますが、
  アクセスがあれば数分〜1 日で「OK」に変わります。

【料金】 アラームは 10 個まで無料（今回 3 個）

【確認方法】
  コンソール: リージョンを「米国東部（バージニア北部）us-east-1」に切り替えて
              CloudWatch → アラーム

 6. 通知メール（SNS）★要対応
--------------------------------------------------------------------------------

【何をしたか】
  通知用の SNS トピックを 2 つ作り、どちらも同じメールアドレスに送るようにしました。

  トピック                         リージョン      送る内容
  -------------------------------  --------------  --------------------------
  SecurityStack-SecurityAlerts...  ap-northeast-1  GuardDuty の検出結果
  MonitoringStack-MonitoringAl...  us-east-1       CloudFront のアラーム

  どちらのトピックも、HTTPS 以外での送信を拒否する設定にしています。

【★あなたがやること】
  AWS から「AWS Notification - Subscription Confirmation」という件名のメールが
  2 通届いています（迷惑メールフォルダも確認してください）。
  それぞれのメールの「Confirm subscription」リンクを開いてください。
  開くまでは通知が届きません（現在の状態: PendingConfirmation = 承認待ち）。

  承認できたかの確認:
    コンソール: SNS → サブスクリプション（東京と us-east-1 の両方）
    → ステータスが「確認済み」になっていれば OK

 8. 今後の運用
--------------------------------------------------------------------------------

【デプロイのしかた】
  infra フォルダで実行します。

    cd C:\Users\nullg\Desktop\board_games\infra
    aws sso login --profile board-game-pia-admin
    cdk diff --all --profile board-game-pia-admin      ← 変更内容の確認
    cdk deploy --all --profile board-game-pia-admin    ← 反映

  通知先は infra/config.local.json から読み込みます。このファイルがない PC で
  デプロイすると、エラーで止まるようになっています（通知先が消えるのを防ぐため）。
  別の PC で作業する場合は、同じ内容のファイルを作るか、環境変数 ALERT_EMAIL を設定してください。

【通知が来たら】
  - GuardDuty: メールのタイトルと種類を確認し、コンソールの GuardDuty → 検出結果で詳細を見る。
    身に覚えのない操作なら、CloudTrail のイベント履歴で「誰が・どこから」を確認する。
  - 5xx エラー: サイトを開いて表示を確認する。直前のデプロイが原因なら、元に戻して再デプロイする。
  - 配信量・リクエスト数: Cost Explorer と CloudFront のレポートで、どこからのアクセスかを確認する。
    攻撃が疑われる場合は WAF の導入を検討する。

【元に戻す方法】
  - 監視アラームをやめる:   cdk destroy MonitoringStack --profile board-game-pia-admin
  - セキュリティ設定をやめる: cdk destroy SecurityStack --profile board-game-pia-admin
      ※ CloudTrail の保存用 S3 バケットは記録を守るために残ります（不要なら手動で削除）
  - ヘッダーをやめる:       web-stack.ts の responseHeadersPolicy の行を消して cdk deploy WebStack
